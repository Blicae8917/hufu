- 评审对象：候选 `0.1.0` 设计正本（`.specify/memory/constitution.md`、`docs/SPEC.md`、

## 0. 如何使用本文件

1. 本文件是**输入**，不是正本。它不修改 Constitution，不新增不变量，不建立任务，
   也不构成对任何 Module 的授权。采纳与否由人类维护者在设计 Pull Request 中裁决。
2. 每一条意见都给出**可独立复核的上游依据**。请不要因为本文件写了就采信；
   请按依据栏自行复核，复核结论与本文件冲突时以你的复核为准，并请更正本文件。
3. 第 3 节是**需要人类裁决的分叉点**，不是可以由 Agent 自行选择的实现细节。
4. 若某条意见与 Constitution 冲突，以 Constitution 为准；本文件的正确处理方式是被驳回，
   而不是反过来削弱不变量。
5. 采纳的条目应落进对应正本（Constitution / ADR / SPEC / ARCHITECTURE / COMPATIBILITY），
   而不是留在本文件里被二次引用。本文件在设计 Pull Request 合并后即失去作用。

## 2. 结论摘要

设计正本在**边界与不变量**这一层的质量高于同类项目平均水平：三轴正交分离、每条事实携带
`fact_status` 与 freshness、"缺失不得写 `0`"、拒绝第二任务正本、以及为自身基础设施设置
"连续三轮无净收益即停止扩充"的效能门禁——最后一条尤其少见，它是给自己装的 kill switch。

主要风险不在已写下的约束里，而在三处尚未表态的地方：Cordis 的实现身份（G1）、
Standalone Profile 的集成方向（G2）、`local` 正本的物理归属（G5）。这三条在设计阶段修改
只是改文字；进入第三张 Module 之后再改就是重写。

| 编号 | 缺口 | 严重度 | 现在不定的代价 |
| --- | --- | --- | --- |
| G1 | "Cordis-compatible" 指向两个不同实现 | 高 | 中立层失效，或长期维护双运行时 |
| G2 | Standalone Profile 的集成方向可能是反的 | 高 | 0.1.0 先建成本更高、覆盖更少的那一半 |
| G3 | 与上游既有服务大面积撞名，未声明 `ctx` 命名空间 | 高 | 插件加载即冲突，语义在同一 Context 内二义 |
| G4 | append-only 多写者缺排序与写者身份 | 中高 | 事件信封补字段 = 无迁移机制下的迁移 |
| G5 | `local` 正本住在被忽略的 `.hufu/` | 中高 | 权威数据不入库、不同步、换机即失 |
| G6 | 无 Schema 迁移策略 | 中 | 重蹈上游持久化无迁移的已知问题 |
| G7 | 纠偏学习是一条软授权通道 | 中 | 从 Journal 反推权限，违反 Constitution I |
| G8 | 上游插件安装契约未进兼容性记录 | 中 | DeepSeek Profile 的生死线未被验证覆盖 |

## 3. 需要人类裁决的分叉点

以下四项无法由实现推导，需要维护者明确表态后才能写进设计正本。

1. **Standalone Profile 中，非 DeepSeek Host 是被 Hufu 驱动，还是由其调用 Hufu？**
   决定 `0.1.0` 至少一半工作量与验收面。见 G2。
2. **Standalone Profile 使用哪个 Cordis 实现？** 上游 `cordis`，还是 `@deepseek-ai/cordis`。
   见 G1。
3. **`local` 任务正本是否需要跨机器？** 决定 Ledger 是否进版本控制。见 G5。
4. **本公开仓库的目标读者是谁？** 若目标包含上游插件生态与未来上游贡献，全中文入口是采纳摩擦；
   上游自身采用 `README.md`（英文）+ `README.zh.md` + i18n 清单的三件套。这是产品定位决策，
   不是文档语言偏好问题。

## 4. 缺口逐条

### G1｜"Cordis-compatible" 指向两个不同的实现

**结论**：设计正本把 Cordis 当作单一稳定框架引用，但上游使用的是改名发布的 vendored fork。
"Cordis-compatible" 目前不是可检验的谓词。

**上游依据**：`vendor/README.md` 记载全部 vendored 包被改名进 `@deepseek-ai` scope，
并附上游对照清单：`@deepseek-ai/cordis` `4.0.1` 源自上游 `cordis` `4.0.0-rc.7`
（`cordiverse/cordis`，提交 `56b3d4f725681cf4556c1a8695a709cc3b6eed74`），
同目录另有本地修改记录；loader / include / group / timer / hmr / logger-console
同样改名，其中 include / group / timer / hmr / logger-console 已指向上游之外的独立仓库。

**影响**：Standalone Profile 二选一，两条路都有代价——依赖 `@deepseek-ai/cordis`，
则"供应商中立 Profile"硬依赖某个 Developer Preview 产品的私有 fork；依赖上游 `cordis`，
则需长期维护双运行时的 Context、Effect 撤销与 dispose 语义一致性，
而这正是全部"可撤销 Effect"不变量的地基。

**建议**：在 ADR 0003 增加"Cordis 实现身份"决策节，显式选择其一并说明理由；
在 `docs/COMPATIBILITY.md` 增加一行记录所选实现及其上游 rc 对应关系，
把 fork 差异作为显式技术债跟踪。倾向意见：选择 `@deepseek-ai/cordis` 并诚实记为
"当前唯一已验证的 Cordis 实现"，优于声称中立而无契约测试支撑。

**验收**：契约测试必须声明它跑在哪个实现上；两种实现都声明支持时，两套测试都必须存在。

### G2｜Standalone Profile 的集成方向可能是反的

**结论**：在 DeepSeek Profile 中 Hufu 是**客人**，在 Standalone Profile 的当前描述中
Hufu 是**主人**。两者被写成对称路径，但成本与覆盖面不对称，而 Standalone 恰恰是
上游 Developer Preview 风险的兜底方案——成本高于主路径的兜底不是有效兜底。

**依据**：`docs/SPEC.md`「使用模式与 Host 边界」与 `docs/ARCHITECTURE.md`「Cordis 插件模型」
描述 Standalone Profile 由 Hufu 组装 Cordis Context 并加载各 Host 的 RuntimePlugin，
即 Hufu 拥有进程与编排；ADR 0003 将"Skill 调用 CLI"降级为过渡与人工 Consumer。
但在非 DeepSeek Host 上，会话、终端与用户输入位于 Host 侧，外部进程既不拥有交互，
也观测不到该会话。

**影响**：对每一个不是 DeepSeek Harness 的 Host，inbound（Host 调用 Hufu）不是过渡形态，
而是永久形态；被降级的方向才覆盖大多数真实使用。现有成功标准
"两个 Profile 对同一事件夹具生成语义一致的 CurrentView"只验证合同层，验证不到这个不对称。

**建议**：把 RuntimePlugin 的服务定义拆成两个方向——inbound Consumer 面（CLI / MCP，一等公民）
与 outbound driver 面（可选，按 Host 能力提供）；`0.1.0` 先交付 inbound。
此举同时更容易守住"MCP 不作为必需运行路径"：MCP 成为若干 Consumer 之一，而非唯一入口。

**验收**：新增一条成功标准，覆盖"Host 侧调用 Hufu"路径的授权校验与 CurrentView 一致性。

### G3｜与上游既有服务大面积撞名，且未声明 `ctx` 命名空间

**结论**：Hufu 计划引入的领域词汇与上游既有服务在同一 Context 内重名而语义不同，
设计正本未做映射，也未声明 Hufu 自己的 `ctx` 命名空间。

**上游依据**：`docs/capability-seams.md` 列出既有 seam，其中与 Hufu 直接重叠的至少包括
`ctx.goals`、`ctx.todo`、`ctx.planMode`、`ctx.workspaceRegistry`、`ctx.storageDomain`、
`ctx.sessionProjections`、`ctx.commands`、`ctx.skills`、`ctx.invariants`、
`ctx.schedule` / `ctx.jobs`、`ctx.credentials`。两处最尖锐：

- `docs/subsystems/workspace.md`：上游 `Workspace` 是"用户工作目录的持久记录"——
  `WorkspaceId` 是生成的 uuid 而非路径，实体包含规范化路径、标题与归属 session 序列。
  Hufu 的 Workspace 指分配给 Owner 的工作场所，二者不可在同一 Context 内并存。
- `docs/subsystems/goal.md`：上游 `ctx.goals` 是**同一 Session 内**的事件溯源目标域，
  `GoalPhase` 为 `active` / `paused` / `blocked` / `complete`，
  `GoalBlockReason` 带稳定的 lower-kebab-case 分类码。Hufu 的目标是**跨 Session、项目级**的——
  这个区分正是 Constitution 想守住的边界，但从未与该同名服务对照。

**建议**：
1. 在设计正本中宣告 Hufu 的 `ctx` 命名空间（例如统一 `ctx.hufu*` 前缀），并禁止裸名注册；
2. 增加一张 Hufu 词汇 ↔ 上游服务的映射表，逐项标注"复用 / 引用 / 改名 / 无关"；
3. 把该问题补进 `docs/handoff/plugin-extension-design-note.md` 的对侧评估问题清单——
   现有四问覆盖了 RoleBinding 与 authorization_scope 映射，未覆盖词汇与 `ctx` key 冲突。

**可直接借鉴的两处上游模式**：

- `ctx.invariants` 是"package-owned invariant registry"。DeepSeek Profile 下，
  Hufu 的部分不变量可以注册进去，从文档约束变为运行时约束。
- 上游 workspace 插件在持久化依赖不可用时**保持 pending，而不是被误读为"空历史"**
  （`docs/subsystems/workspace.md`）。这是"缺失不得写 `0`"原则的运行时形态，
  建议原样纳入 Hufu 的启动依赖处理规则。

### G4｜append-only 多写者缺排序与写者身份

**结论**：Constitution V 把"每个可执行 WorkItem 恰有一个当值 `owner`"写为 MUST，
但在无协调的多写者 append-only 日志上，该不变量只能被**检测**，无法被**强制**。

**依据**：`docs/ARCHITECTURE.md`「本地 JSONL 规则」要求 `occurred_at` 使用真实墙钟且仅追加；
`docs/SPEC.md`「V1 明确不做」排除 Lease 与多主机协调（该取舍本身合理）。
两条并存时，跨写者的因果序无法确定，并发绑定无法在写入时拒绝。

**建议**：
1. 把该不变量表述为"回放时检测冲突并 fail closed，暴露为冲突态 `fact_status`"，
   与"缺失不得伪装成已知"的整体哲学一致；
2. 事件信封**现在就**加入 `writer_id` 与每写者单调序号（混合逻辑时钟或等价物）。
   往已经在运行的 append-only 日志补排序字段，正是 G6 所述"没有迁移机制去做的迁移"。

### G5｜`local` 正本住在被版本控制忽略的目录

**结论**：Constitution 要求 `.hufu/` 排除在版本控制之外，同时又让 `local` 正本的
append-only Ledger 拥有任务生命周期，且位于 `.hufu/`。两条合起来意味着**权威数据
不入库、不同步、无备份、协作者不可见**。

**依据**：`.specify/memory/constitution.md`「系统边界」与 `docs/ARCHITECTURE.md`
「本地运行态与安全边界」；仓库 `.gitignore` 已包含 `.hufu/`。

**说明**：对 `github` / `gitlab` 正本，该规则正确——本地内容只是投影与缓存。
问题仅出现在 `local` 正本上。

**建议**：物理拆分两类本地状态——`.hufu/cache/`（忽略，投影与派生视图）与
`.hufu/ledger/`（**纳入版本控制**，本地正本事件）。这同时缓解 G4：版本控制的合并冲突
把并发追加变成显式冲突，而不是静默覆盖。若裁决为"`local` 正本按定义是单机的"，
则需在 SPEC 显式写明该限制，而不是留给用户发现。

### G6｜无 Schema 迁移策略

**结论**：设计已引入 Schema Version 与"迁移必须提升 Schema Version，不能静默改义"，
但未定义迁移**机制**。

**建议**：现在就定为**读时 upcast**——Ledger 记录永不改写，由版本感知的 reader
在读取时升级为当前内部表示；每个 Schema 版本必须保留其 upcast 函数与回放夹具。
这是一句话的决策，可避免一次重写，并与"仅追加、当前视图是回放结果"完全兼容。

### G7｜纠偏学习是一条软授权通道

**结论**：`docs/handoff/plugin-extension-design-note.md` 预留的六个插座中，
第 1 项（`CorrectionObservation` → 纠偏学习）与其余五项性质不同：它让历史改变未来建议。
现有约束"只优化建议，不产生或扩大授权"方向正确但不充分。

**建议**：补两条边界——纠偏必须**可归因到具体人类**（不得由 Agent 自产自销后回喂），
且**可撤销**（撤销后 CurrentView 必须能确定性重建为不含该纠偏的状态）。
否则它构成一条从 Journal 反推权限的隐蔽路径，而 Constitution I 明令禁止该路径。

### G8｜上游插件安装契约未进兼容性记录

**结论**：DeepSeek Profile 依赖的 out-of-tree 插件安装路径在上游是真实且有规范的，
但 `docs/COMPATIBILITY.md` 的"每次升级必须验证"清单尚未覆盖它。

**上游依据**（`packages/bundle/README.md` 与 `packages/boot/app-boot/README.md`）：

- 安装命令：`dsh plugin --profile <name> add <package>`；
- bundle 定义：npm 包 manifest 声明 `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }`，
  未声明该字段的包会 fail loud；
- profile 位置：`$DSH_HOME/profiles/<name>`（Harness home 解析顺序为 `$DSH_HOME`，否则 `~/.dsh`），
  目录内含 `package.json`（out-of-tree 依赖 + `dsh.profile.bundles` 有序层列表）
  与用户自己的 `cordis.patch.yml`；
- 上游自陈的已知限制两条，均直接影响 Hufu：
  1. bare 包名解析依赖 Loader 内部模块加载，生产 bin 需要可选原生 peer `node-addon-require-builtin`；
     否则调用方必须使用可解析的相对 / file 说明符或自备解析钩子；
  2. **用户 patch 对匹配到的条目是整块替换 `config`，不做深合并**——任何一次覆盖都会丢掉未重述的字段。

**建议**：把上述四点写入 `docs/COMPATIBILITY.md` 的必验清单；第一张实现 Module 必须包含
一条真装真卸的契约测试（装入 profile → 服务可用 → 卸载 → Tool、Event Listener 与其他 Effect
全部撤销干净）。现有成功标准已包含"卸载后清理"，建议将其绑定到这一具体契约上。

**附带一处记录偏差**：`docs/COMPATIBILITY.md` 记录 `@deepseek-ai/dsh` `0.1.0-rc.5`，
与所复核提交内 `apps/cli` 的清单版本一致；但上游无 tag / release，
已发布 npm 产物与源码提交之间没有可证明的绑定关系。建议在该文件中把
"源码基线"与"已发布产物版本"分列两栏，并注明二者身份不可互相推断。

## 5. 工程与项目层建议

**P1｜治理文档的重述密度已经构成漂移风险。**
"不是任务正本"这条不变量在 Constitution、SPEC、ARCHITECTURE、ADR 0001、ADR 0003、
AGENTS 与 README 各表述一遍。项目自身的设计规则第 1 条是"一项事实只有一个权威所有者"，
但该规则尚未应用于文档本身。建议：每条不变量指定唯一 normative 出处（Constitution），
其余文件只允许链接、不允许复述；ADR 写决策与被拒方案，SPEC 写用户可见行为，
ARCHITECTURE 写结构。

**P2｜给 `0.0.1` Python 基线一个明确死期。**
"当前 Python 是已实现基线、不得描述为已迁移"这句免责声明在多份文件中重复出现，
Constitution 的强制门禁也仍锁在 Python 命令上，而 `0.0.1` 的 `source=native|external`
已被目标设计判定迁移。建议在设计 Pull Request 中直接写死：第一张实现 Module 合并时，
以 tag 保留 `0.0.1` 历史并从主线删除 Python 实现与对应门禁。一次决策，消除多处补丁式说明。

**P3｜设计正本目前不在版本控制中。**
`.specify/`（含 Constitution）、`docs/adr/`、`docs/COMPATIBILITY.md`、`docs/handoff/`
当前均为未跟踪状态——它们既不是被忽略，也尚未提交。法律层级最高的文件不应只存在于工作树。
建议在设计 Pull Request 的第一个提交中纳入。

**P4｜效能门禁缺度量协议与人工基线，因而当前不可判定。**
"连续三轮代表性试点无净收益即停止扩充"是整套设计中最有价值的约束，但缺两样前置物：
其一是**度量协议**（什么算一次"协调唤醒"，墙钟如何归因到 Hufu 编排而非模型推理，
返工如何判定），其二是**当前无 Hufu 的人工基线**。二者不在第一张 Module 之前定下来，
"净收益"必然退化为回溯性主观判断。建议趁设计 Pull Request 仍开放时，
在代表性项目上采集人工基线；公开仓只保留脱敏方法与聚合结果。

**P5｜缺威胁模型，且存在一条具体的注入路径。**
Hufu 会把外部 Issue 文本投影进 CurrentView，操作者或模型据此生成"下一步指令"。
外部 Issue 正文是任何人可写的内容，这构成一条**不可信内容 → 指令**的通路，
现有设计正本未覆盖。建议增加一条不变量：Provider 投影文本一律视为不可信数据，
进入生成指令时必须以引用或转义形式出现，不得作为指令语句拼接；并配一条契约测试
（投影内含指令样式文本时，输出中必须位于引用块内，而非指令体内）。

此外，凭据来源目前表述为"由 Provider 的常规凭据机制管理"，未落到具体机制。
命令行工具登录态、Host 的凭据 seam、环境变量令牌三者的失败模式与审计面不同，
应在 Provider Module 的 Spec 中定死。

**P6｜`authorization_scope` 为自由文本，导致一条成功标准无法自动验证。**
SPEC 的成功标准含"生成的下一步文本……不超出已记录范围"，但 scope 当前是自然语言列表，
机器无法判定越界。建议现在就在合同中预留结构化字段（路径 glob、仓库、命令类别），
即使 `0.1.0` 仍以自由文本填充——理由同 G4：给 append-only 事件补字段是最难的一类迁移。
