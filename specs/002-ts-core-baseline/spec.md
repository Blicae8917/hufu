# Feature Specification: 当前工作基线与历史基线退役

**Feature Branch**: `002-ts-core-baseline`

**Created**: 2026-08-15

**Status**: Accepted

**Input**: User description: "GitHub Module Issue #2（M1）：建立零 Cordis 依赖的领域核心骨架，并在同一交付中退役 0.0.1 历史基线、换成一套当前有效门禁。不实现 connect / doctor / status / handoff，不接入外部任务系统。"

**Parent Issue**: [#2](https://github.com/Blicae8917/hufu/issues/2)

## User Scenarios & Testing *(mandatory)*

本模块的用户是仓库维护者与贡献者，不是最终操作者。它交付的是「能继续开发 0.1.0」的当前工作基线，而不是任务协调产品功能。

### User Story 1 - 只面对一套当前验证入口 (Priority: P1)

维护者克隆本仓库后，按照 README 的快速开始，只看到一套当前有效的安装与验证步骤，并能在本机跑通。文档、自动化规则和实际门禁说的是同一件事。

**Why this priority**: 现在仓库同时声称目标栈尚未实现、又把 Python 命令写成强制门禁。不先收成一套当前基线，后续模块会继续双轨漂移。

**Independent Test**: 按 README 在干净环境执行全部当前验证步骤，全部通过；仓库中不再出现第二套被写成「当前必须」的验证步骤。

**Acceptance Scenarios**:

1. **Given** 维护者拿到本模块合并后的主线，**When** 阅读 README 快速开始与贡献规则中的交付门禁，**Then** 二者指向同一套命令，且都能在本机成功完成。
2. **Given** 维护者按快速开始完成验证，**When** 检查公开文档是否把未交付的协调能力写成已经可用，**Then** 找不到此类陈述。
3. **Given** 一次改动仓库内容的交付，**When** 运行当前门禁，**Then** 通过门禁只证明本次本地验证，不暗示已经发布或验收。

---

### User Story 2 - 历史 0.0.1 仍可完整取出 (Priority: P1)

维护者需要核对或复现最初公开发布时，能检出一个冻结标签，并按当时的步骤跑通当时的验证，而不被本模块的新基线覆盖掉那段历史。

**Why this priority**: 宪法要求首个新基线模块合并时用标签保留 0.0.1。没有这条，退役就变成不可逆丢失。

**Independent Test**: 检出历史标签后，按该标签内文档完成当时的验证；该标签内的实现与门禁保持原样。

**Acceptance Scenarios**:

1. **Given** 本模块已经合并，**When** 维护者检出保留 0.0.1 的标签，**Then** 仍能按该标签文档完成当时的信封校验与测试。
2. **Given** 该历史标签，**When** 查看其门禁与实现，**Then** 它们仍属于 0.0.1 当时的基线，而不是被新基线改写后的内容。

---

### User Story 3 - 最小信封校验仍然可用 (Priority: P2)

维护者仍能拿一份任务信封样例，判断它是否符合已经发布的最小合同：合法输入得到成功摘要，非法输入被拒绝且不产生副作用。

**Why this priority**: 0.0.1 对外只交付了这件事。新基线可以换实现载体，但不能让公开仓库在过渡期失去唯一可演示能力。四个产品命令仍不在本模块。

**Independent Test**: 使用仓库提供的合法样例与若干非法样例，分别得到成功与明确失败，且失败不改写仓库业务状态。

**Acceptance Scenarios**:

1. **Given** 仓库提供的合法任务信封，**When** 维护者运行最小校验入口，**Then** 得到表示有效的机器可读摘要，退出表示成功。
2. **Given** 缺少目标、未知来源或空授权范围的信封，**When** 维护者运行最小校验入口，**Then** 校验失败，错误进入标准错误输出，退出码表示合同或输入无效。
3. **Given** 任意非法信封，**When** 校验失败，**Then** 仓库中没有因此产生连接、账本或外部调用。

---

### User Story 4 - 产品协调命令明确尚未提供 (Priority: P2)

操作者如果尝试做 0.1.0 发布门里的协调工作（连接项目、健康检查、看当前视图、交接），系统必须明确表示这些能力尚未提供，而不能假装成功或输出像那么回事的结果。

**Why this priority**: 防止本模块范围膨胀，也防止文档与入口让人以为四命令已经可用。

**Independent Test**: 分别请求 connect / doctor / status / handoff，均得到「尚未提供」类失败，且不创建运行态。

**Acceptance Scenarios**:

1. **Given** 本模块交付后的程序入口，**When** 请求 connect、doctor、status 或 handoff，**Then** 每项都以明确失败结束，而不是成功或占位成功。
2. **Given** 上述失败，**When** 检查工作区，**Then** 没有因此出现项目连接、账本或缓存目录。

---

### Edge Cases

- 新基线门禁与文档不一致时，交付必须失败，不得只改其中一侧。
- 历史标签缺失或无法按标签复现 0.0.1 验证时，本模块不得合并。
- 贡献者只安装了旧基线运行时、未安装新基线运行时时，当前主线验证应失败并给出可理解原因，而不是悄悄改走旧基线。
- 信封校验遇到无法读取的文件或无法解析的内容时，必须按合同/输入无效失败，不得当作有效。
- 本模块不得因为「骨架需要演示」而访问网络、读取凭据、启动后台服务或写入外部系统。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 仓库 MUST 只公布一套当前有效的安装与验证入口；文档、自动化规则和实际门禁 MUST 在同一交付中同时指向这套入口。
- **FR-002**: 与当前入口并行的历史实现和历史门禁 MUST 在同一交付中从主线移除，不得留下「现在仍要跑」的第二套步骤。
- **FR-003**: 合并本模块前 MUST 存在可检出的 0.0.1 历史标签；该标签 MUST 仍能按当时文档完成当时验证。
- **FR-004**: 维护者 MUST 仍能校验最小任务信封：合法样例成功，非法样例失败；失败 MUST 使用合同/输入无效的退出语义，并把原因写到标准错误输出。
- **FR-005**: 最小信封合同 MUST 继续区分本机来源与外部来源，MUST 要求非空目标、非空授权范围和非空终止条件；外部来源的引用若出现则 MUST 为非空文本。本模块 MUST NOT 把该合同升级为 GitHub/GitLab/local 正本模型。
- **FR-006**: 程序入口 MUST NOT 提供 connect、doctor、status、handoff 的成功路径。
- **FR-007**: 本模块 MUST NOT 引入网络访问、凭据存储、后台服务、遥测或外部副作用。
- **FR-008**: 领域核心 MUST 保持供应商中立，且 MUST NOT 把任何 Host 插件运行时或编排框架当作核心依赖。
- **FR-009**: 公开文档 MUST NOT 把未交付能力（四命令、账本、GitHub 投影、插件、会商、网页）描述成已经实现。
- **FR-010**: 当前开发版本保持维护者已批准的 `0.1.x` 系列；本模块 MUST NOT 自行提升版本的前两位。
- **FR-011**: 每次改仓库内容的交付 MUST 能在 Windows 与 POSIX 上完成当前门禁；本地通过只证明所声明的本地证据。
- **FR-012**: 实现任何新的可观察行为前 MUST 先有一条会失败的测试，再写生产代码。

### Key Entities

- **当前基线**: 主线上贡献者必须使用的安装、验证与门禁集合；同一时刻只能有一套。
- **历史基线**: 用标签冻结的 0.0.1 公开发布；只用于复现，不再作为主线门禁。
- **最小任务信封**: 已发布的目标、来源、授权范围、终止条件与可选外部引用；本模块只校验，不把它变成项目账本。
- **产品命令**: `connect`、`doctor`、`status`、`handoff`；本模块明确不交付。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 未接触过本仓库的贡献者，按 README 能在 15 分钟内完成安装并得到一次全部通过的当前验证（Windows 与 POSIX 各至少一次）。
- **SC-002**: 检出 0.0.1 历史标签后，按其文档能在 15 分钟内复现当时的成功验证。
- **SC-003**: 对 README、贡献指南和自动化规则做一次通读，找不到第二套被写成当前必须执行的验证步骤。
- **SC-004**: 对仓库提供的合法信封样例，最小校验入口 100% 成功；对缺少目标、未知来源、空授权范围的样例，100% 失败且不改变仓库业务状态。
- **SC-005**: 分别请求四个产品命令时，100% 明确失败，并且工作区不出现项目连接或账本。
- **SC-006**: 抽查产品规范、架构说明和 README 的「当前范围 / 项目状态」陈述，未交付能力均被标为尚未实现。

## Assumptions

- 目标用户是本仓库维护者与贡献者；最终操作者的协调工作由 #3、#4 交付。
- 目标技术栈、零 Cordis 依赖、以及「首个新基线模块必须同时退役历史实现并替换门禁」已由 #2、Constitution 和 ADR 0003 裁决，本规格不再重开。
- 0.0.1 唯一对外能力是最小信封校验；本模块默认保留该能力作为最小可运行入口，而不是改成只能打印版本的空壳。
- `0.0.1` 的 `native` / `external` 信封语义保持不变；正本迁移到 `local` / `github` / `gitlab` 属于后续模块。
- 测试运行器和打包工具的具体选择属于 Plan，本规格只要求：工具集最小、足以证明上述场景，且不整包照搬上游单仓的全部基础设施。
- 本模块不发布正式版本；当前开发版本号保持 `0.1.0`。
- 不需要为本模块采集效能试点；它不增加操作者协调能力。

## Out of Scope

- 四个产品命令、本机账本、CurrentView、授权记录本体、冷启动序列
- GitHub / GitLab 投影
- Host 插件运行时、双入口夹具对等、真装真卸
- 零拷贝决策流、LoopX、会商、网页界面、出站运行时
- 跨机器同步、数据库、消息队列、守护进程
